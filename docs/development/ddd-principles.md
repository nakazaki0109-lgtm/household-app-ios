# DDD の判断基準

要件ごとに「どの層に何を置くか」を決めるための基準。このリポジトリは軽量な層構成を取っており、要件が小さいうちはこれを崩さない。複雑な要件が来たときだけ、下の「重くする条件」を満たすか確認して拡張する。

## 現状の層構成 (README.md のアーキテクチャ節と同じ)

| 層 | 置き場所 | 置くもの | 置かないもの |
|---|---|---|---|
| Domain | `HouseholdApp/Domain/` | 値オブジェクト、業務ルール (不変条件、計算) | SwiftUI・SwiftData への依存 |
| Models | `HouseholdApp/Models/` | SwiftData の `@Model` (永続化の形) | 業務ルールの判断 |
| Services | `HouseholdApp/Services/` | ユースケース (取得・保存・集計の手順) | 画面の状態、UI 文言の組み立て |
| Views | `HouseholdApp/Views/` | 入力受付と表示 | 業務ルール、永続化の詳細 |

依存の向きは Views → Services → Domain / Models。Domain は誰にも依存しない。この向きを逆にする変更 (Domain が SwiftData を import するなど) は、要件が求めていても実装前にユーザーへ相談する。

## 要件を層に振り分ける

1. **「〜であってはならない」「〜以上」「形式は〜」のような不変条件** → 値オブジェクト。`Money` のように、不正な値を生成時点で弾く。Service や View で `if amount < 0` を書かない。理由: 検査を書く場所が散らばると、必ずどこかで抜ける。
2. **計算・判定 (超過したか、残額はいくらか)** → Domain の値オブジェクトのメソッド。副作用が無く、シミュレータ無しでテストできる。
3. **「保存する」「月ごとに集める」のような手順** → Service。手順の途中の業務判断は Domain に委ねる。
4. **保存項目の追加** → Models。既存データの移行が要るなら、実装前にユーザーへ確認する (壊すと戻せない)。
5. **画面** → Views。表示用の整形は `Domain/Formatters.swift` の流儀に合わせる。

Swift のコードを伴わない要件 (ビルド・配布の自動化、設定ファイル、スクリプト) は、この層構成の対象外。DDD を無理に当てはめず、そのリポジトリの既存の流儀 (置き場所、テストの書き方) に従う。

## 重くする条件 (要件ごとに判断)

次の条件を満たさない限り、Aggregate・Repository プロトコル・ドメインイベントは導入しない。この規模で先回りして入れると、コード量だけが増える。

- **Aggregate**: 複数のオブジェクトを「常に一緒に整合させる」必要が要件から読み取れる (例: 予算の合計とカテゴリ別予算の上限を同時に守る)。整合の境界が1つのオブジェクトに収まるなら、ただの Entity / 値オブジェクトで足りる。
- **Repository プロトコル**: 永続化を差し替える要件があるか、Service のテストで SwiftData の `ModelContext` を使うのが実際に重い。今の Service は `ModelContext` を受け取る形でテストできている。
- **ドメインイベント**: 「〜したら別の処理を起こす」が要件に複数現れ、Service に直接書くと結合が強くなる。

満たす場合は、導入する理由を `docs/adr/` に残す (domain-modeling の基準: 戻すのが高コスト、文脈が無いと意外、実際の代替案があった、の3つが揃うときだけ)。

## ユビキタス言語

- 要件に出てくる名詞は、`CONTEXT.md` の用語と、コード上の型名・変数名を一致させる。`CONTEXT.md` が無ければ、最初の用語が確定した時点で作る。
- 要件の用語が既存の型名とずれている (要件では「明細」、コードでは `Transaction` など) ときは、黙って片方に寄せず、domain-modeling スキルで用語を確定してから実装する。コードだけ直すと、次に要件を読む人が混乱する。
- `CONTEXT.md` は用語集であり、実装の詳細 (どのクラスが何をするか) は書かない。
