# レビューの観点

レビュー役のサブエージェントが、担当する観点ごとに読む。目次:

- 共通: 指摘の質を保つ規則
- 観点1: 正確性とセキュリティ
- 観点2: 設計基準
- 観点3: requirements.md との適合
- 重要度の付け方

## 共通: 指摘の質を保つ規則

指摘の数より、指摘の確からしさを優先する。外れた指摘が混ざると、当たった指摘まで読まれなくなるため。

- 指摘は、該当コードを実際に読んで確認してから書く。「〜かもしれない」だけの推測は書かない。
- 指摘には失敗シナリオを付ける。「どの入力・状態で、何が起きて、どう困るか」を具体的に書けないものは、指摘にしない。
- 差分に含まれない既存コードの問題は、今回の変更が悪化させた場合だけ指摘する。
- 好み (命名、コメントの量、書き方の流儀) は指摘しない。基準に反する点だけを指摘する。

## 観点1: 正確性とセキュリティ

Swift / SwiftUI / SwiftData のコードで、特に見る点。

- **異常系の握りつぶし**: `try?` で失敗を捨てて、結果が空・nil のまま処理が進む。`context.save()` の失敗を無視する。保存に失敗したのに画面は成功したように見えるものは重い。
- **強制アンラップ・範囲外アクセス**: `!`、`as!`、`array[0]`、`first!` が、空のデータや未設定の状態で落ちる。
- **境界値**: 0 円、月の切り替え (月末・年またぎ)、空のカテゴリ、非常に大きい金額 (`Int` の加算のオーバーフロー)。
- **日付とタイムゾーン**: `Calendar` や `DateFormatter` のロケール・タイムゾーン依存で、月の判定がずれる。
- **SwiftData**: リレーションの削除規則によるデータ消失、`#Predicate` の条件の誤り、`ModelContext` をスレッドをまたいで使う、保存の抜け。
- **並行性**: UI の更新がメインスレッドで行われない。クロージャの循環参照。
- **状態管理**: `@State` / `@Binding` / `@Query` の取り違えで、画面が更新されない。入力の検証が View だけにあり、Service や Domain で守られていない。

スクリプトやシェルのコードで見る点。

- 入力を検証せずにコマンドへ渡している (コマンドインジェクション)。
- 途中で失敗したのに、後続の処理が続く。中断すべき失敗を無視している。
- 再実行すると壊れる、または二重に作成される (冪等でない)。

セキュリティで見る点 (Swift・スクリプト共通)。

- **秘密情報がリポジトリに入っていないか**: パスワード、トークン、APIキー、アプリ用パスワード、2FAコード、電話番号やメールアドレスなどの個人情報。差分だけでなく、追加された設定ファイルとログ出力も見る。`.gitignore` で除外すべきファイルが除外されているか。
- 秘密情報を、ログ・エラーメッセージ・画面に出力していないか。
- 秘密情報を、平文のファイルや `UserDefaults` に保存していないか (Keychain を使うべきもの)。
- 外部から受け取った値を、検証せずにパス・URL・コマンドに使っていないか。

## 観点2: 設計基準

次の2ファイルを読み、その基準に照らす。

- `.claude/skills/implementing-requirements/references/ddd-principles.md` — 層の置き場所、依存の向き、Aggregate などを導入する条件、用語の扱い
- `.claude/skills/implementing-requirements/references/swift-compile-time.md` — コンパイル時間のコーディング規約、モジュール分割の条件

指定された Swift のアプリコードだけが対象。スクリプトや設定ファイルには適用しない。

`scripts/review_scope.py` の出力にある「依存の向きの違反 (機械検出)」は、確認済みの事実として扱い、指摘に加える。機械では検出できない点を、人が読んで確認する。

- 不変条件 (「0以上」「形式は〜」) の検査が、値オブジェクトではなく Service や View に書かれていないか
- 業務ルール (超過判定、集計の計算) が View に書かれていないか
- 根拠のない Aggregate・Repository プロトコルなどが導入されていないか
- 要件の用語と、型名・変数名がずれていないか
- コンパイル時間の規約: 複雑な式、型注釈の欠如、大きい `body`、複雑な `#Predicate`、`final` / `private` の欠如

## 観点3: requirements.md との適合

`requirements.md` がある場合だけ担当する。

1. `python3 .claude/skills/implementing-requirements/scripts/requirements_tasks.py requirements.md` で、番号付きの機能要件 (F)・受け入れ条件 (A)・制約 (C)・スコープ外 (X) を得る。
2. 差分に関係する項目それぞれについて、「満たす / 満たさない / 検証不能」を、根拠 (ファイル:行、テスト名) 付きで判定する。読んで確認できないものは「検証不能」にする。
3. X (スコープ外) が実装されていれば指摘する。
4. 差分と無関係な項目は、判定せず省く。全項目を埋める必要はない (実装の網羅確認は implementing-requirements の役割)。

## 重要度の付け方

- **高**: データ消失、クラッシュ、秘密情報の漏洩、要件の受け入れ条件を満たさない、誤った金額や集計結果。修正してからでないとマージできないもの。
- **中**: 特定の条件で誤動作する、設計基準への明確な違反、テストの欠落 (Domain の不変条件など)。
- **低**: 直すと良いが、放置しても害が小さいもの。
