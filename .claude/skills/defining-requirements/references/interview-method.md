# 質問の作り方

`grilling` と `domain-modeling`（いずれも mattpocock/skills 由来、`.claude/skills/NOTICE.md` 参照）の考え方を、要件定義向けに組み直したもの。

## 決定木で考える

要件は、決定が別の決定にぶら下がる木になっている。たとえば「複数端末で使うか」が決まらないと、「データをどこに置くか」は聞いても意味がない。

- **フロンティア**: 前提の決定がすべて済んでいて、今聞ける質問
- フロンティアの中から、影響が大きいものを1〜3問選んで聞く
- 答えが返ったら木を組み直す。決まったことで、聞かなくてよくなった質問は捨て、聞けるようになった質問を足す
- ある質問の答えが、まだ開いている別の質問に依存するなら、その質問は後回しにする

質問が尽きる（フロンティアが空になる）まで、木のどの枝も飛ばさない。

## 質問の順序

上流から下流へ。上が決まっていないと下は決められない。

1. **誰の、どんな痛みか**: 誰が使うか、今どうしていて何が困るか、頻度はどのくらいか
2. **スコープ**: 何をやるか。同じ重さで、何をやらないか。「やらない」を明示すると、後の「これも入ってると思った」を防げる
3. **正常系の振る舞い**: 主な操作の流れ
4. **例外・境界**: データが0件のとき、上限を超えたとき、途中でやめたとき、削除したとき
5. **受け入れ条件**: どうなっていれば完成と言えるか。外から観察できる形で
6. **制約・非機能**: 対応環境、性能、データの保持、プライバシーなど

## 選択肢の作り方

- 2〜4個。互いに排他にする
- 推奨案を先頭に置き、`(Recommended)` を付け、選ぶ理由を description に書く。理由を添えるのは、ユーザーが推奨を鵜呑みにせず判断できるようにするため
- 「やらない」「今回は見送る」も選択肢として入れる。要件は足す方向に膨らみやすいため
- 選択肢の説明には、選んだ場合に何が起きるか（ユーザーから見た結果）を書く。技術用語で説明しない
- 「その他」は自動で付くので、自分で作らない

## 具体シナリオで境界を突く

抽象的に「どうしますか」と聞くと、答えが曖昧なままになる。具体例で聞く。

- 悪い例: 「削除の扱いはどうしますか」
- 良い例: 「先月の支出を1件削除したら、先月の予算の残額は自動で戻りますか？」

## コードと食い違ったら指摘する

ユーザーの説明と既存コードの挙動が違うときは、その場で示して、どちらが正しいか聞く。

例: 「今のコードでは予算超過しても登録できますが、『超過したら登録できない』という理解で合っていますか」

## 聞かないこと

- **調べれば分かる事実**: コード、README、既存ドキュメントから自分で調べる
- **実装方式**: 使うライブラリ、クラス構成、DB のスキーマは設計であって要件ではない。ただし「オフラインで動く」のように、ユーザーから見える制約として現れるものは要件として聞く

## 用語と決定の扱い

- `CONTEXT.md` があれば読み、そこにある用語で質問する。ユーザーが定義と違う意味で語を使ったら、その場で指摘する
- 用語の曖昧さが解けない、または新しい用語を定義する必要が出たときは、`domain-modeling` スキルを呼んで `CONTEXT.md` を更新する。`requirements.md` に用語集を混ぜない
- 「後から変えるのが高くつく」「理由を知らないと驚かれる」「実際に選択肢を比べて選んだ」の3つが揃う決定だけ、`domain-modeling` の ADR として残すことを提案する。1つでも欠けるなら、`requirements.md` への記録で十分

## requirements.md への書き方

- 機能要件は「〜できる」の形で1行に書く
- 受け入れ条件は「〜のとき、〜になる」の形で、観察できる結果を書く
- 実装の詳細（クラス名、画面遷移の実装方法）は書かない。読む人が、実装を変えても要件が有効なままにするため
- 1項目は1行。長くなるなら項目を分ける（スクリプトは1行単位で扱う）
