# 既存スキルの観点別レビュー

既存の `SKILL.md` （とその同梱リソース）を、次の観点ごとに順番にチェックし、観点ごとに「現状 → 直す案」を1行でまとめる。全観点で問題なしなら、その旨を明記して終える（無理に指摘を作らない）。

## 観点

1. **粒度とサイズ**
   - SKILL.md は一貫して1つの仕事をしているか
   - 本文が500行に近い/超えているのに、まだ全部本文に書かれていないか
   - → 超えていれば、常時必要な部分と特定条件でしか要らない部分を仕分け、後者を `references/` へ

2. **参照ファイルの切り出し**
   - 特定の分岐・ドメインでしか使わない詳細が本文に混ざっていないか
   - `references/*.md` へのポインタに「いつ読むか」が書かれているか（ファイル名だけのリンクになっていないか）

3. **スクリプト化の余地**
   - 決定的な手順（採番、集計、雛形生成、フォーマット変換、検証）がプローズの手順として書かれていないか
   - 同じような多段階のコマンド列を、SKILL.mdの中で何度も手順として説明していないか（→ スクリプト化してSKILL.mdでは実行コマンドだけ示す）

4. **スクリプトの単体テスト**
   - `scripts/` にスクリプトはあるが `scripts/tests/` が無い、または薄すぎないか
   - ロジック本体とCLIエントリポイントが分離されていて、テストしやすい形になっているか
   - 異常系（不正入力、既存ファイルの上書きなど）がテストされているか

5. **サブエージェント設計の分離**
   - スキルがサブエージェントを呼んでいるのに、その指示がSKILL.md本文に埋め込まれていないか
   - `agents/*.md` に切り出されている場合、役割・入力・出力・制約の4点が書かれているか

6. **description（トリガー精度）**
   - frontmatterの `description` が「何をするか」と「いつ使うべきか」の両方を含んでいるか
   - 曖昧な表現（「〜を手伝う」程度）で終わっていて、具体的なトリガー文脈が書かれていないか

7. **Why の説明**
   - 「MUST」「NEVER」のような強い命令が、理由の説明なしに置かれていないか
   - 理由を説明せず高圧的な指示だけを並べている箇所は、背景にある制約や失敗事例を一言添える形に直せないか

## 出力フォーマット

観点ごとに1行、次の形式でまとめる:

```
- [観点名] 現状: <何が問題か> → 提案: <どう直すか>
```

問題がない観点は次のように書く:

```
- [観点名] 問題なし
```

最後に、直す案をそのまま適用してよいか、あるいは提案だけに留めるかをユーザーに確認する。適用してよいと言われた場合のみ、実際にファイルを編集する。
