# Swift のコンパイル時間を抑える設計

Swift のビルドが遅くなる主因は、(1) 型推論の負荷が高い式、(2) 1つの変更で再コンパイルされる範囲の広さ、(3) モジュール境界の無さ、の3つ。実装中は (1) をコーディング規約で、(2)(3) を設計で抑える。効果は感覚で判断せず、`scripts/build_timing.py` で測る。

## 目次

- コーディング規約 (常に守る)
- モジュール分割 (条件を満たすときだけ)
- 計測と、遅い箇所の直し方

## コーディング規約 (常に守る)

各規約の理由は、型推論の探索が式の複雑さに対して急激に重くなるため、または変更の影響範囲を狭めるため。

- **1つの式に演算子と型推論を詰め込まない。** `+` `??` 三項演算子 `map`/`reduce` を1行に重ねる代わりに、名前付きの中間変数に分ける。特に、数値リテラルと変数が混ざった算術式と、`+` による文字列連結 (文字列補間にする) は重い。
- **型が自明でない箇所は型注釈を書く。** 要素が混在しうる配列・辞書リテラル、複数行クロージャの戻り値 (`{ (x: Int) -> Money in ... }`)、トップレベル定数。
- **SwiftUI の `body` を大きくしない。** 画面の塊ごとに独立した `struct` の View に切り出す (`Views/Components/` がその置き場所)。1つの `body` に `ViewBuilder` の分岐と修飾子を大量に積むと、型チェックが遅くなるうえ、エラーの場所も分かりにくくなる。目安は、`body` が画面1つ分の高さを超えたら分割する。
- **`#Predicate` は単純に保つ。** マクロ展開後の式も型チェックされる。条件が複雑なら、単純な条件で取得してからメモリ上で絞る (`BudgetService` の `saveCategoryBudget` が既にそうしている)。ただし、取得件数が増えうる場合は件数の見積もりをコメントに残す。
- **アクセス制御を最小にする。** クラスは `final`、内部でしか使わない宣言は `private` / `fileprivate`。コンパイラが依存関係と最適化の範囲を狭く見積もれる。
- **1ファイルに1つの主な型。** 頻繁に変わる型と広く参照される型を同じファイルに置かない。変更のたびに、その型を参照する全ファイルが再コンパイル対象になるため。
- **プロトコルの乱用と過度なジェネリクスを避ける。** 具象型で足りる箇所を抽象化すると、型推論が探索する候補が増える。

## モジュール分割 (条件を満たすときだけ)

`Domain/` をローカル Swift Package に切り出すと、次の利点がある。

- Domain は SwiftUI・SwiftData に依存しないので、`swift test` だけでテストできる (シミュレータ起動が要らない)。
- Domain を変えない限り、Domain の再コンパイルは走らない。

ただし切り出しは、`project.yml` の書き換え、`public` 修飾の追加 (別モジュールから使う型・メソッド・イニシャライザ全て)、ファイルの移動を伴う。要件の実装のついでに黙って行わない。次の条件のうち2つ以上を満たすときに、ユーザーへ提案する。

1. `Domain/` のファイルが概ね10を超え、業務ルールが増え続けている
2. ユニットテストの実行時間の大半が、シミュレータ起動とアプリのビルドに費やされている
3. 計測 (`build_timing.py`) で、Domain 由来の遅い箇所が繰り返し出る

提案では、移す範囲 (どのファイルか)、`project.yml` の変更内容、`public` を付ける対象を示し、ユーザーが承認してから着手する。一度の作業で行うのは、承認を得た1回の切り出しまで。

## 計測と、遅い箇所の直し方

実装が一段落したら測る。

```bash
python3 .claude/skills/implementing-requirements/scripts/build_timing.py run
```

- `HouseholdApp.xcodeproj` が無ければ、先に `xcodegen generate` を実行する (ファイルを追加したときも同様。`.xcodeproj` は Git 管理外で、`project.yml` から生成される)。
- クリーンビルドで、関数本体 200ms・式 100ms を超えた箇所を、遅い順に出す。終了コードは、遅い箇所があれば 1、なければ 0、ビルド失敗なら 2。
- 遅い箇所が出たら、上の規約に沿って直す: 式を分ける → 型注釈を足す → View を切り出す。直したら再計測し、消えたことを確認してから次へ進む。しきい値は `--function-ms` `--expression-ms` で変えられる。
- 直せない、または直すと可読性が大きく落ちる場合は、そのまま残して最終報告に書く。黙って放置しない。
